## 1. Grill-Me — flesh out a vague idea

The operator has a half-formed idea. Don't just agree — *grill* it until concrete:

```
- Ask SHARP questions, one at a time: "who exactly is the user? what problem is PAID for to solve?"
- Challenge assumptions: "why this, not [simpler alternative]?"
- Pull toward specifics: scope, what success looks like, non-goals (what is DELIBERATELY not done)
- Stop once the idea can be PRD'd. Don't over-grill (see sk58: don't over-shape).
```

Different from sk58 (shaping general operational goals) — Grill-Me is specifically *product/feature ideas* → ready to become a spec. Output: an idea with a clear user, problem, scope, and success metric.

## 2. To-PRD — conversation → document

```python
from prd import to_prd
doc = to_prd(conversation_or_notes, title="Referral Feature")
# → markdown PRD: Problem · Goals · Non-Goals · Users · Requirements (P0/P1/P2) · Success Metrics · Risks · Open Questions
print(doc.markdown)
```

A good PRD = concise but complete: problem first (not solution), measurable goals, explicit non-goals, prioritised requirements (P0 mandatory / P1 / P2), success metrics, risks. Export via sk8 (DOCX/PDF) if you need a format.

## 3. To-Issues — PRD → task breakdown

```python
from prd import to_issues
issues = to_issues(doc)   # → list {title, body, labels, estimate, depends_on}
# push to GitHub/Linear/Jira via sk6 (API) or output a markdown checklist
```

Each issue: actionable title (verb), acceptance criteria, rough estimate, dependency. Small enough to do in 1 session (in line with sk23 task-breakdown). Order by dependency → hand off to sk16 for execution.

## 4. TDD superpower

```
1. SPEC → write tests from the requirement FIRST (tests = executable spec)
2. RED  → run them, they must fail (proof the tests actually test)
3. GREEN→ write the minimal code until the tests go green
4. REFACTOR → tidy up, tests stay green
```

Test first = designing the API from the user's side + an automatic regression net. Combo sk56 (Eval) + sk16 (impl) + sk25 (CI gate). For migration (sk25) TDD is a mandatory safety net.

## 5. Internal-Comms — professional communication

Technical context → clear communication for a non-technical/stakeholder audience: status update, incident report, decision memo, RFC. Principles: BLUF (bottom line up front), honest about risk, one clear CTA. Complement to sk20 (tone) but in a professional/corporate format.
