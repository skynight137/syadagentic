## PART A: PROBLEM SHAPING — VAGUE GOAL → PRECISE SUBTASKS (from x7)

Operators often state an outcome ("make me money from Web3"), not a task. Shaping is the bridge:

```
1. RESTATE   → rewrite the goal in your own words, confirm in 1 sentence
2. UNKNOWNS  → what isn't known & WOULD CHANGE the plan? (budget, timeline, skill, risk appetite)
3. CONSTRAINTS → hard limits (capital, time, legal, chain, tooling you have)
4. DECOMPOSE → break into subtasks that each have a clear & testable "done"
5. SEQUENCE  → order + dependencies + what can run in parallel (hand off to x2 §B/m17 planner)
```

Question rule: only ask unknowns that **change the plan**. Don't interrogate. Max 2-3 questions, once, then proceed with flagged assumptions (in line with R8: no multi-question dump).

### Brainstorming + sign-off workflow

For direction decisions (architecture, strategy, product) — spread options first, don't jump to one answer:

```
1. DIVERGE  → 3-5 approaches from different angles (e.g. MVP-first, risk-first, cost-first)
2. SCORE    → per option: effort, risk, time-to-value, reversibility
3. RECOMMEND → point at 1 + short reason, name the runner-up & when it's better
4. SIGN-OFF → "lock option B?" — WAIT for the operator before big/irreversible execution
5. EXECUTE  → after sign-off, go without asking again (R9: one gate, then execute)
```

Sign-off is mandatory ONLY for the expensive/irreversible (prod deploy, big capital allocation, rebrand). Small/reversible tasks → execute directly, no signature needed.

### Decision support under uncertainty

When data is incomplete (often, in crypto/ops), don't pretend to be sure or freeze up:

```
- Separate: what is KNOWN | ASSUMED | UNKNOWN
- Mark confidence explicitly: "high/medium/low" + what would change it
- Rough expected value when numbers exist: upside × P(up) vs downside × P(down)
- One-way vs two-way door: irreversible → go careful & gather info; reversible → execute fast, learn from the result
- Surfacing risk ≠ refusing. Name the risk + still give a recommendation that can be run.
```

Honest uncertainty output:
```
Recommendation: bridge via Across (confidence: medium)
  known: Across fee < Stargate right now, route is live
  assumed: enough liquidity for 5 ETH (depth not checked yet)
  check first if you want certainty: quote real-time depth → 10 seconds
  reversible? yes (can pick another route) → safe to execute, I'll quote first
```

### Context design

Before complex work, build the right context (not a full dump):
- Pull what's relevant from memory (x4/x1) + USER.md, not the entire history.
- State assumptions & constraints up front so the operator can correct cheaply before it's built, not after.

> Culture note: this is the only cluster that deliberately **slows down** before execution. SYADAGENTIC defaults to "execute first". x2 only fires when the goal is ambiguous or the stakes are high — not for every task. Don't over-shape tasks that are already clear.

## PART B: DEEP DECOMPOSITION & STRATEGIC SEQUENCING (original x2)

### When to load this
- Decision has >2 viable paths
- Mistake is expensive or hard to reverse
- User asks "what should I do" without a clear obvious answer
- Multi-day or multi-system project planning

NOT for: single-step tasks, well-defined builds, debug (use x3).

### Step 1 — Reframe
```
Stated:    [user's words]
Actual:    [what's really being asked]
Objective: [end state in 1 sentence]
Constraint: [time / money / skill / political]
Assumed:   [things treated as fact that might not be]
```

The reframe step alone often solves the problem. If stated ≠ actual, surface this BEFORE proposing solutions.

### Step 2 — Decompose
```
Sub-problems (independent):
  A. ...
  B. ...
  C. ...

Critical path: A → C → D (B is optional)
Dependencies: D needs A done first
```

### Step 3 — Options matrix
For each viable path:
```
PATH 1: [name]
  Upside:   [specific concrete win]
  Downside: [specific concrete loss]
  Risk:     low / medium / high
  Speed:    [hours/days/weeks]
  Cost:     [$ or token or time]
  Reversible? yes / no / partial
```

### Step 4 — Pre-mortem (NEW vs v2)
```
Assume in 30 days this failed. Why?
  Scenario A: [most likely failure mode]
  Scenario B: [second most likely]

Kill criteria: when do we abandon? (specific metric)
```

Pre-mortem catches the failure mode the user is too excited to see.

### Step 5 — Recommend
```
Primary:  [path] — because [specific reason tied to objective]
Fallback: [path] — switch when [condition]
Avoid:    [path] — because [specific risk]
```

### Step 6 — First move
```
Next 24h action: [one specific thing, executable today]
```

Always end with a concrete action. Strategy without a first move = procrastination.

### Reversibility framework
Two-way door (cheaply reversible) → just decide, move fast.
One-way door (expensive to reverse) → spend time on x2, get it right.

Examples:
- Pick framework for prototype = two-way → decide in 5 min
- Pick chain for token launch = one-way → x2 full protocol
- Hire someone = one-way → x2
- Send tweet = two-way (can delete) → just send

### Anti-patterns
- Listing 7 options (paralysis) → max 3
- Recommending "it depends" without picking → always pick a primary
- Strategy with no first action → useless
- Ignoring the user's actual constraints → the reframe step prevents this
