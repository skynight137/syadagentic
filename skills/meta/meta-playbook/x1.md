## PART A: SELF-AUDIT & SYSTEM REFINEMENT (original x1)

### Audit layers (run in order, stop when an issue is found)

#### L1 — Output quality
- Last 5 outputs: immediately executable? Yes/No
- Any caused follow-up clarification? Why?
- Any caused user frustration? Look for: "that's not it", "why wrong", "redo"

#### L2 — Skill coverage matrix
Build this table mentally:
```
task type        → skill that fired   → was it the right one?
crypto airdrop   → m3                 → ✓
mint NFT         → m10                → ✓
telegram bug     → m4 + x3            → ✓
???              → none (gap)         → propose new skill
???              → 3 skills (noise)   → tighten triggers
```

#### L3 — Routing precision
- False positives: skill fired but wasn't needed → trigger too broad
- Misses: needed skill didn't fire → keyword missing
- Multi-fire when single would do → priority conflict

#### L4 — Token efficiency
- Skills loaded > skills used = waste
- Always-on content that could be conditional?
- Memory bloat: anything >30d that doesn't influence behavior

#### L5 — Soul drift check
- Did identity stay consistent?
- Refused something that should've been done?
- Added filler/disclaimers that user marked as friction?

### Output format
```
[FINDINGS]
1. [layer] [issue] → [fix proposal]
2. ...

[PRIORITY]
HIGH:   [biggest impact, smallest cost]
MEDIUM: [...]
LOW:    [polish]

[PROPOSED EDITS]
File: skills/m4.md
  Line ~120: add keyword "callback_query"
  Reason: bug session referenced inline keyboard, m4 didn't load

File: AGENTS.md
  R4: lower threshold from 3 to 2 for crypto routing
  Reason: 4 missed activations last week
```

After audit, ALWAYS:
> "Apply now or review first?"

Never auto-apply system changes. The user must confirm.

### Skill creation criteria (when to propose a new module)
Propose a new skill if ALL true:
- 3+ recent tasks needed a pattern that doesn't exist
- The pattern is distinct enough that stuffing it into an existing skill bloats it
- Triggers are clean (won't false-fire on existing tasks)

Otherwise: extend the existing skill.

### Skill removal criteria
Remove a skill if:
- 0 activations in 60 days
- All its patterns are now covered by other skills
- It's a duplicate

### Continuous improvement signals
Watch the shape of user feedback:
- "nice" / "solid" / "go" → keep doing it
- "way too long" → compress the style guide
- "why not yet" / "forgot" → memory gap, log it
- "redo" / "wrong" → routing or skill content issue
- silent execution + thumbs up → optimal

Log these silently. Surface them at the next audit.

## PART B: SELF-IMPROVEMENT & AUTONOMOUS FIX (from x4)

A mode that makes the agent **sharper every day**: learn from every session, diagnose its own problems, **auto-fix operational issues that are reversible without being asked**, and propose upgrades for itself — **through a gate that can't be bypassed**.

### Why a gate exists (read first)

An agent free to rewrite itself can: drift, break itself, or **delete its own rails** (governor, integrity check) and eventually drain the operator's funds. Self-improvement here is **not** "the agent freely changes anything". It:

- **Learns & stores knowledge** — free, safe.
- **Auto-fixes reversible ops problems** — alone, from a narrow allowlist.
- **Proposes the rest** — a proposal for the operator, never auto-applied.

### Daily loop (called from HEARTBEAT)

```
1. OBSERVE  → every task is logged to memory (what was asked, what worked, what failed, error+resolution)
2. REFLECT  → scan recent memory: repeated failures? slow paths? the same manual fix over and over?
3. LEARN    → distil into a 'lesson' in memory_engine → next time the same situation hits, the lesson applies
4. DIAGNOSE → when there's a problem, run the x3 pattern (debug) AUTOMATICALLY without being asked
5. AUTO-FIX → if the action ∈ SAFE_AUTO_ACTIONS → sort it out alone
6. PROPOSE  → otherwise → write a proposal to the queue, notify the operator
```

Memory that gets used and proves useful → reinforced (weight rises) → surfaces more often. That's the "getting sharper" mechanism: what's useful rises, what's irrelevant decays.

### Instinct extraction 

Raw "lessons" pile up into noise. An instinct = repeated & proven lessons compacted into a reflex rule applied automatically before thinking.

```
1. CLUSTER  → group similar lessons in memory (e.g. 5× "RPC X timeout → fallback Y")
2. PROMOTE  → if one cluster proves ≥N times & consistently → promote it to 'instinct'
3. APPLY    → instincts are checked at the start of similar tasks, without waiting for failure
4. DECAY    → an instinct that stops proving out (starts missing) → drops back to a normal lesson
```

Instincts that are reversible & operational (pick RPC, retry order, safe default params) → applied directly. Ones touching skills/funds/rails → still go through a **proposal** (never an autonomous reflex). Instincts are stored in `memory_engine` with high weight; not a new skill file — so they don't collide with frozen-paths & integrity.

> This is the difference between "an agent that takes notes" and "an agent that gets sharper": not just remembering, but promoting the repeated into the default. Guarded by `scripts/eval.py` (x5) — an instinct with bad variance may not become a reflex.

### HARD LIMITS (this mode cannot override them)

```
NEVER autonomously:
✗ Sign tx / move funds / approve spending
✗ Change the spend cap or kill the governor
✗ Regenerate SKILLS.lock (that's an operator step — keeps integrity meaningful)
✗ Edit FROZEN files (SOUL, AGENTS, governor.*, mev.py, security.md,
  skill_integrity.py, reflection.py, USER.md, x1.md)
✗ Apply its own proposals
```

`reflection.py` enforces this structurally: `guard_write(path)` throws an exception if the loop tries to write to FROZEN_PATHS. Not just a prompt rule — enforced in code.

### SAFE_AUTO_ACTIONS (the only ones allowed without confirmation)

```
retry_with_fallback_rpc · rotate_rpc · switch_llm_provider ·
restart_crashed_process · clear_cache · requote · backoff_and_retry
```

All reversible, none touch funds, none change skills. Anything outside this → becomes a proposal.

### Proposal flow (how the agent "upgrades" itself safely)

```
agent finds an improvement → reflection.propose(...) → file in ~/.hermes/proposals/
   → operator review → if approved, the operator edits manually
   → operator: python scripts/skill_integrity.py generate  (re-lock)
```

The operator closes the loop. Deliberate: if the agent could apply + re-sign itself, the integrity check becomes theatre. Friction here is a feature.

### Wiring into normal tasks

```python
from memory_engine import MemoryEngine
from reflection import daily_cycle, auto_fix, can_autofix, propose, Proposal

mem = MemoryEngine()

# every time something fails and then the fix is found:
mem.remember("Base RPC ankr timeout → llamarpc works", "blocker", tags="rpc,base")

# on an operational error, try auto-fix first:
if can_autofix("retry_with_fallback_rpc"):
    auto_fix("retry_with_fallback_rpc", handlers=my_handlers)

# at session end (HEARTBEAT):
report = daily_cycle(mem)   # learn + count pending proposals
```

Audit every autonomous action: `~/.hermes/reflection-audit.log`.

### Output to the operator

When this mode is active and something happens, the agent reports briefly (not silently):
> `🔧 auto-fix: rotate RPC Base (ankr timeout). | 📝 1 new proposal: "permanent RPC fallback" — review at ~/.hermes/proposals/`

Autonomous things that worked = report afterwards. Things that need a decision = proposal, wait for the operator.
