# x5 — Agentic Eval & Self-Critique (NEW in v4.1)

Measure yourself before the operator measures you. Structured eval, adversarial self-critique, and **variance testing** (run a task N times → check consistency). Completes x1 (system audit) & x4 (self-improve loop). Tool: `scripts/eval.py`. **Read/measure only — touches no funds, edits no skills.**

---

## Why it exists

x1 audits structure, x4 learns from failures. x5 fills the gap: **quantitative proof** that output is right & stable. "Looks correct" ≠ "correctly consistent". Eval = a net before the operator hits the bug.

## 1. Adversarial self-critique (before sending risky output)

Before sending output that's expensive when wrong (code that moves funds, destructive DB queries, strategy), run one *refute* round:

```
1. Write the candidate output.
2. Take the SKEPTIC role: "how does this fail / go wrong?" — default to 'something is wrong'.
3. Check every claim: evidence? edge case? untested assumption?
4. Passes → send. Fails → revise, repeat.
```

Different from the m0 reflection loop (which checks quality/completeness): x5 self-critique **hunts for ways the output is factually/logically wrong**, not just untidy.

## 2. Structured eval

```python
from eval import Eval, Case
ev = Eval("mint-detector")
ev.add(Case(input="opensea.io/.../1", expect=lambda r: r["fn"]=="mintPublic"))
ev.add(Case(input="zora.co/collect/...", expect=lambda r: r["price_eth"] > 0))
result = ev.run(target_fn, repeat=1)
print(result.summary())   # pass_rate, failures with input + actual vs expect
```

Pattern: collect real cases (especially ones that failed before — pull from memory/x4), assert properties, run on every logic change. Regression net.

## 3. Variance testing (rare — high value)

LLMs/agents are non-deterministic. A task that "sometimes works" is a trap. Measure it:

```python
from eval import variance
v = variance(task_fn, input=payload, runs=10)
print(v.report())
# → consistency: 0.7 (7/10 the same), modes: {"ok":7,"timeout":2,"wrong_fn":1}
#   verdict: FLAKY — don't auto_confirm this task until >0.95
```

Decision rules:
- consistency ≥ 0.95 → may go into automation/`auto_confirm`.
- 0.7–0.95 → needs per-run confirmation, or fix the prompt/logic.
- < 0.7 → **don't automate**. Find the variance source (ambiguous prompt? flaky RPC? race?) — goes to x6.

High variance on a funds path = block until stable. This stops "usually correct" automation from draining the balance on run 8.

## 4. Optimization loop (eval-driven)

```
baseline eval → change 1 variable (prompt/model/param) → re-eval → compare →
keep if pass_rate rises & variance falls → repeat. One variable per iteration.
```
Don't change many things at once — you won't know what worked. A winning result → record it to memory (x4) as a lesson; if it touches a skill file → proposal (frozen-paths, operator ack).

## 5. LLM-as-judge (production-grade)

For output that can't be asserted with `==` (writing quality, reasoning correctness, helpfulness) → use another LLM as judge, with an explicit rubric:

```python
from eval import llm_judge
verdict = llm_judge(
    output=candidate,
    rubric=["factual & evidenced?", "answers the actual question?", "any hallucination?"],
    scale=5,                    # score 1-5 per criterion + reasons
)   # → {scores:{...}, pass: bool, reasons:[...]}  via model_registry cascade
```

Rules so the judge isn't theatre:
- **Concrete rubric**, not "good/bad" — separate criteria + scale.
- **Judge ≠ producer** — different model/role from the one producing the output (avoid self-love bias).
- **Panel for high stakes** — N judges, take the majority (reduces the judge's own variance).
- **The judge gets evaluated too** — check judge consistency with `variance()`; a flaky judge isn't trusted.
- Combine with self-critique (§1): judge = outside perspective, self-critique = internal refute.
